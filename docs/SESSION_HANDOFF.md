### 4. AWS deployment strategy review + Lambda migration (Terraform, unapplied)

- Decided: migrate to **Lambda (via OpenNext) + CloudFront + S3**, keep RDS Postgres exactly as-is (already correctly sized), drop the in-memory graph cache in favor of direct-to-Postgres queries per request (this also incidentally fixes a correctness bug: multiple ECS tasks could previously disagree on graph state).
- **App code changes** (already live, not just infra): new `src/backend/services/graph/pg-graph.service.ts` (`PgGraphService`) replaces the deleted `InMemoryGraphService`/`GraphBootstrapService`. `GraphService` interface (`src/backend/services/graph/graph-types.ts`) is now async. `ChainValidationService` updated accordingly. `ensureServicesReady()` bootstrap pattern removed entirely from `src/backend/wiring/container.ts` and all API routes. `pg.Pool` max reduced from 10 to 3 in `src/backend/repositories/postgres/db.ts` (Lambda concurrency = many small pools, not one big one).
- **Infra changes** (Terraform written, never applied): new `infra/modules/lambda_app/`, `infra/modules/cloudfront_lambda/`. Deleted `infra/modules/alb/`, `ecs_service/`, `ecr/`, `cloudfront_alb/`. Updated `security/`, `scheduler/` (now targets a placeholder Lambda instead of `ecs:RunTask` — no real daily-publish logic exists, see section 5), `observability/` (added real CloudWatch alarms that didn't exist before), `network/` (NAT Gateway now disabled by default). Rewired `infra/environments/dev/` and `infra/environments/prod/`. Updated `infra/TERRAFORM_CHECKLIST.md`.
- Did a real local OpenNext build spike (`npx open-next build`) to verify the actual Lambda artifact shape before writing Terraform against it — found and fixed a real secret-leak bug in the process: Next.js's standalone build copies the local `.env` into the build output, and OpenNext then bundles that into the deployable Lambda zip. Fixed via `open-next.config.ts`'s `buildCommand` override to strip it post-build. `open-next.config.ts` also disables the ISR/incremental-cache machinery (SQS/DynamoDB) since this app has zero ISR usage — keeps the deployed topology to just Lambda + CloudFront + S3.

### 6. Major game-rule redesign — anchor-player puzzle model
Replaced the old fixed "start player → ordered required-sequence → target player" puzzle format with: **3-5 named "anchor" players; the player picks any of them to start on, any to end on, and visits the rest in any order** — no repeats, still alternating PLAYER→CLUB→PLAYER.
- New migration `db/migrations/006_daily_puzzle_anchor_players.sql`: new `daily_puzzle_players` join table replaces the old `start_player_id`/`target_player_id`/`required_player_ids`/`required_player_names` columns (also had to drop and recreate the `v_published_daily_puzzles` view, which depended on the dropped columns).
- New solver `scripts/puzzle-generation/solver.ts` (`findShortestAnchorChain`) — tries every start/end ordering of the anchor set with a branch-and-bound backtracking search, returns the **true shortest** connecting chain (not just the first one found, unlike the old DFS), and returns `null` if the anchor set turns out unsolvable. Has its own test file, `solver.test.ts`, with a test that specifically proves it doesn't just grab a longer decoy path.
- Updated `ChainValidationService`/`ChainValidator` interface (now takes `anchorPlayerIds: number[]`, no more `startPlayerId`/`targetPlayerId`/`requiredPlayerIds`), `DailyPuzzleDTO`/`DailyPuzzle` domain types (`anchorPlayers`/`anchorPlayerIds` replace the old start/target/required fields), `daily-puzzle.repository.ts` (new SQL joining the new table), `/api/validate-chain`, `/api/daily`.
- `scripts/seed-dev.ts` rewritten to call the new solver instead of trusting hand-typed, unverified data.
- `src/app/page.tsx`: first chain step now picks from the anchor set (not an auto-injected fixed start), unordered anchor chips with visited checkmarks replace the old numbered "required sequence," removed the synthetic start/target node injection entirely (the player's own first/last submissions now are the start/end).
- Updated `docs/CONTEXT_MEMORY.md` to describe the new rules.

### 7. Date picker restriction + streak correctness (most recent work)
- New `GET /api/daily/dates` endpoint returns the real published-date range plus the server-authoritative `today` (Postgres `CURRENT_DATE`, not client clock).
- `/api/daily?date=X` now 404s cleanly for an explicitly-requested unpublished date instead of silently substituting the latest puzzle (a "strict" mode added to `getPublishedPuzzleByDate`).
- Fixed a latent timezone bug found along the way: `puzzle.date` was coming back as a full UTC timestamp (pg driver's `DATE`→JS `Date`→ISO conversion, which can shift the calendar date depending on server timezone) — now a plain `YYYY-MM-DD` string via `to_char()` in SQL, consistently everywhere.
- **Streak fix**: `refresh_user_streak` (in `src/backend/repositories/postgres/game-result.repository.ts`) now only fires when the solved puzzle's actual `puzzle_date` equals `CURRENT_DATE` — backfilling an old puzzle updates your lifetime solve count but never touches the streak. `getUserStats` now also shows `currentStreak: 0` once the last on-time solve is more than a day stale, without needing a new solve to "notice" (matches how Wordle visually shows a broken streak the moment you've missed a day).
- **Removed the parallel client-side `localStorage` streak system** (`src/app/streakStorage.ts`, `src/app/streakCalculator.ts` — deleted, along with their test) since it had no way to implement "only counts if solved on the correct day" correctly and would have kept showing a different, wrong number next to the now-correct server one. UI consolidated to one server-backed "Streak" card + a "Solves" (lifetime) card.
- Frontend date picker: `min`/`max` bound to the real published range, client-side validation rejects out-of-range/gap dates with an inline message, shows a "past puzzle won't count toward streak" notice when viewing a non-today puzzle.
- All of the above verified live via curl + browser (not just unit tests) — including deliberately backdating a streak row in Postgres to confirm the staleness display logic.
